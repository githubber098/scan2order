# Claude instructions for scan2order

## Commit messages

Whenever code changes are made, **always compose a detailed git commit message**. This project has two collaborators working in separate Claude sessions with no shared context — the commit message is the only way each person's Claude understands what the other did. Write as if the reader has never seen this codebase before.

Every commit message must include:

- **Subject line** (≤72 chars): imperative mood, says what changed
- **Body — per-file bullet list**: for every file touched, name it explicitly and describe *what specifically changed inside it* (not just "updated" — say what function/section/behaviour changed and how)
- **Why**: one or two sentences explaining the motivation or the decision behind the change, including any alternatives that were considered and rejected
- **Architecture context**: if the change touches a key design decision (storage backend, API format, auth flow, LLM integration), explain what the current approach is so a reader with no prior context understands the system state after this commit
- **Impact / action needed**: anything a collaborator must do after pulling — e.g. rebuild Docker image, run a migration, pull an Ollama model, update an env var

Do not commit silently or with a one-liner unless the user explicitly says so.

## Current architecture (keep this section up to date)

- **Session storage**: SQLite by default (`backend/storage/user_store.py`) — file lives at `/app/data/sessions.db` inside the container, mounted as `./data:/app/data` in docker-compose. Set `MYSQL_URL=mysql://user:pass@host:3306/db` to switch to MySQL/MariaDB instead; the `_MySQLDB` wrapper in `user_store.py` translates all SQL automatically (placeholder style, upsert syntax, DDL types). A commented-out MySQL service is in `docker-compose.yml` for easy opt-in. No external Redis or Upstash dependency.
- **LLM ranking + OCR (one model)**: Local Ollama running `qwen2.5vl:3b` by default serves BOTH the product-ranking fallback (`backend/ranker.py:_ollama_rank`, fires only when the algorithmic ranker finds no winner) AND handwriting OCR (`backend/ocr.py`). Qwen2.5-VL is OCR-specialised and ~3GB — lighter and faster on the prod box than gemma4:e2b was. (History: started on gemma4:e2b, but on the Ryzen 4800U / 16GB / CPU-only box it needed 1100px+ to read handwriting and ran ~40-60s; qwen2.5vl reads at lower res and is smaller.) Selected via `OLLAMA_MODEL`, reached via `OLLAMA_HOST`. NOT auto-pulled — run `docker compose exec ollama ollama pull qwen2.5vl:3b` after first start. No Groq / no API key needed. OCR image size is capped by `OCR_MAX_DIM` (default 1200; lower → faster, raise if a scan returns empty).
- **OCR**: `backend/ocr.py` is vision-LLM-first with a Tesseract fallback, chosen by `OCR_BACKEND` (`auto` = VLM then Tesseract; `ollama`; `tesseract`). `extract_grocery_list()` is **async** — the vision call hits Ollama's OpenAI-compatible `/v1/chat/completions` with the image as a base64 data URL; Tesseract runs via `asyncio.to_thread`. Tesseract is kept only as a no-model/no-RAM fallback (it reads handwriting poorly).
- **Store API calls**: All httpx, no Playwright. BigBasket: listing-svc search + mapi cart. Blinkit: `__NEXT_DATA__` SSR parse for search, `/v2/client/user_cart/` for cart. Zepto: BFF gateway search + bulk-widget-data cart, SHA-256 signed.
- **Deployment**: Docker + docker-compose on homeserver, exposed via Cloudflare Tunnel (no open inbound ports). Auto-updates from GitHub via systemd timer every 5 min.
- **Auth flow (web)**: Passwordless — phone (Twilio SMS OTP) OR email (SMTP OTP). `backend/auth.py` (normalise + 6-digit OTP + HMAC session cookie), `backend/sms.py` (Twilio), `backend/email_sender.py` (SMTP); all three fall back to printing the OTP to the server log if their provider env vars are unset. `users` table has nullable-unique `phone` + `email` (an account can have one or both); `otp_codes` is keyed by `target` (phone or email). Endpoints: `/api/auth/send-otp` + `/api/auth/verify-otp` (login, `{channel,value[,code]}`), and `/api/auth/method/send-otp` + `/api/auth/method/verify` (link a 2nd method to the logged-in account — verified by OTP, rejects contacts already used elsewhere). After logging in with one method the web UI shows a banner prompting to add+verify the other. `get_or_create_user(channel,value)` auto-creates accounts on first verified login.
- **Auth flow (mobile / store sessions)**: Mobile logs in to each store via WebView, cookies sent to backend → stored in SQLite `sessions` table. Web UI can enter an 8-char link code generated by mobile to share the store session. (Store auth is separate from the user-account auth above.)
